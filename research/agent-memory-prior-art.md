# Prior art in agent-memory MCP servers

Research for [#21](https://github.com/CameronWragg/data-driven-second-brain/issues/21). Sources were read on 2026-10-25. Repository links are pinned to the commit that was current that day.

**Question:** What can the Second Brain learn from existing agent-memory and knowledge MCP servers about tool surface and granularity, about teaching Agents when to read and when to write, about avoiding write spam and duplicates, and about reported failure modes?

## Short answer

1. **Server `instructions` are the only guidance an Agent is sure to see.** Claude Code defers MCP tool definitions by default and loads only tool names and server instructions at the start of a session, and it cuts instructions at 4,096 characters. Our SPEC doesn't define any server instructions yet. They should be the first thing we write, with the most important rules first.
2. **Never return the whole store.** The reference memory server's `read_graph` returns everything. Users report it reaching 50k to 80k tokens after a few weeks of use. Our design already avoids this with summaries from `search`, full text from `get`, and a small `context`. We should make sure every tool has a size budget.
3. **Say what not to write, as well as when to write.** The strongest prior art sets an explicit bar for writing. Claude Code's auto memory "skips anything it can derive from the codebase". Serena says "Do not add: quick-read facts; generic language/framework knowledge; one-off task notes…". This matches ADR-0002 and should appear in the instructions almost word for word.
4. **When a write looks like a duplicate, give the Agent a decision to make, not just a score.** Basic Memory lists at most 3 near neighbours after a create. It hides the scores and offers a three-way choice: same topic → edit the existing note, related → add a relation, unrelated → do nothing. It also leaves out notes the new note already links to. Its threshold (0.70 on bge-small-en-v1.5) was measured against real rewrites. We should borrow all of this, and tune our threshold with `brain eval`.
5. **Exact-match deduplication isn't enough.** The reference server dedupes only on identical names and identical observation strings, so paraphrases pile up. Server-side LLM extraction and deduplication (Graphiti, Mem0) solves this, but needs an LLM and background workers, which ADR-0005 rules out. Similarity-based checks are the right middle ground for us.
6. **Common failure modes** are context blow-up, observations piling up with no way to reorganise them, destructive tools with no undo, secrets being kept, memory acting as a lasting prompt-injection surface, and Agents simply not writing. Our SPEC already handles most of these through git, the secret check and scoping. It doesn't yet treat Recollections as untrusted data.

## 1. Tool surface and granularity

**Reference server: many fine-grained mutation tools and one way to read everything.** The server has `create_entities`, `create_relations`, `add_observations`, `delete_entities`, `delete_observations`, `delete_relations`, `read_graph`, `search_nodes` and `open_nodes` ([README](https://github.com/modelcontextprotocol/servers/blob/ef9808f71090d0db3eda99e2af2ba78f1086f4fb/src/memory/README.md)). Search is a case-insensitive substring match over names, types and observations ([index.ts L656–666](https://github.com/modelcontextprotocol/servers/blob/ef9808f71090d0db3eda99e2af2ba78f1086f4fb/src/memory/index.ts#L656-L666)). Every read returns entities with all of their observations. Issue #3953 reports that "a single memory_read_graph call can consume 50k-80k+ tokens… after 6 weeks of daily usage", and that there is "no way to fetch entity names first, then selectively load observations".

**Newer designs consolidate writes and make reads progressive.**
- Anthropic's API memory tool is **one** tool with six commands (`view`, `create`, `str_replace`, `insert`, `delete`, `rename`). Its `view` truncates files over 16,000 characters and accepts `view_range` for paging ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).
- Basic Memory separates browsing, ranked search and reading: "Use bm_list for one folder, bm_find for recursive names…, bm_search for ranked retrieval…, and bm_read for note and file content. bm_read supports bounded lines, sections, and token budgets." Writes split into "bm_write creates notes and explicitly overwrites them; bm_edit never creates missing notes", and edits are guarded by a checksum the Agent got from a read ([server.py L243–266](https://github.com/basicmachines-co/basic-memory/blob/4bcfc0665744960f514a0ff61f4f432aa8cfe54f/src/basic_memory/mcp/server.py#L243-L266)). By default `write_note` refuses to overwrite an existing note unless it gets `overwrite=True`, and `expected_checksum` makes the overwrite conditional on the note being unchanged ([write_note.py L91–95](https://github.com/basicmachines-co/basic-memory/blob/4bcfc0665744960f514a0ff61f4f432aa8cfe54f/src/basic_memory/mcp/tools/write_note.py#L91-L95)).
- Serena gives the Agent "the full memory *name list* up front", then relies on a root memory (`mem:core`) that references more specific memories. It argues that "given an intelligent agent and well-structured references, search is unnecessary - and it adds noise" ([docs](https://github.com/oraios/serena/blob/abb0a0f01b94bc8050086f0fb860077d17730324/docs/02-usage/045_memories.md)).
- Claude Code auto memory loads only an index (`MEMORY.md`, at most the first 200 lines or 25KB, "one line per memory"), and "Claude reads [topic files] on demand" ([memory docs](https://code.claude.com/docs/en/memory)).
- Mem0's plugin exposes only **one** MCP tool, `search_memories`, because writing happens outside the Agent's control (§3).

**Client-side limits apply.** Claude Code warns when an MCP tool's output goes over 10,000 tokens and limits it to 25,000 tokens by default ([MCP docs](https://code.claude.com/docs/en/mcp)).

**Lessons for us**
- Our split between `search` (summaries) and `get` (full bodies) is the same progressive pattern the field moved to after `read_graph`. Keep it, and never add a "dump everything" tool.
- `get` takes `ids[]` with no limit. Give it a size budget, for example a maximum number of IDs or a character budget with a continuation, so it stays under Claude Code's 10k-token warning. `context` needs a budget too, which is already a question in #24.
- A single batched `write` tool matches where the field is heading: the API memory tool uses one tool with commands, and Basic Memory has a small set of verbs. We can borrow Basic Memory's optimistic concurrency. An `update` or `supersede` could carry the `updated` timestamp or content hash the Agent read, and be rejected if the file has changed since. This matters because hand edits and other `serve` processes can change a file between `get` and `write` (SPEC §10–11).
- The spec's tool annotations ([schema](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)) are cheap to add. Mark `context`, `search`, `get`, `history` and `promotion` with `readOnlyHint: true`. Mark `write` as non-read-only and destructive, since it can delete.

## 2. Teaching Agents when to read and when to write

**Where guidance reaches the Agent.**
- The MCP spec describes `instructions` as "guidance describing the server and its features… e.g., by including it in a system prompt. It should… not duplicate information already in tool descriptions" ([schema L688–696](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)).
- In Claude Code, tool search is on by default: "Only tool names and server instructions load at session start". Server instructions "help Claude understand when to search for your tools". Claude Code also cuts text: "Server instructions, and the description of a tool that loads upfront: 4,096 characters", so "put critical details near the start". A server can ask for one tool to load upfront by setting `_meta["anthropic/alwaysLoad"]: true` ([MCP docs](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search)).
- Basic Memory reached the same conclusion from experience, and says so in a code comment: "A newly-connected model only sees the server `instructions` for free — everything else (the ai_assistant_guide resource, tool descriptions) requires it to choose to fetch" ([server.py L237–242](https://github.com/basicmachines-co/basic-memory/blob/4bcfc0665744960f514a0ff61f4f432aa8cfe54f/src/basic_memory/mcp/server.py#L237-L242)).
- The reference server ships **no** instructions. Its README instead gives an example system prompt for users to paste in ("Always begin your chat by saying only 'Remembering…'…"), and notes that "the prompt… will help the model determine the frequency and types of memories created" ([README](https://github.com/modelcontextprotocol/servers/blob/ef9808f71090d0db3eda99e2af2ba78f1086f4fb/src/memory/README.md)). So it is up to each user whether the Agent is taught anything.
- When the Anthropic API memory tool is enabled, the API adds a system-prompt protocol automatically: "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE… ASSUME INTERRUPTION" ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).

**What the read guidance says.** Every system puts reading first, before work starts:
- Graphiti's rules say "Always search first… before beginning work" and "Search before suggesting" ([cursor_rules.md](https://github.com/getzep/graphiti/blob/5c27edfa8d3e0f49b2571bcebb4261bcc89ee037/mcp_server/docs/cursor_rules.md)).
- Basic Memory says "When a request may draw on the user's notes, use bm_search… before answering from memory".
- Mem0's single tool description contains its whole read policy: "Use it before repeating investigation or when earlier decisions, fixes, commands, or results may help" ([mcp_server.py L22–26](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/integrations/claude-code-plugin/core/mcp_server.py#L22-L26)).

**What the write guidance says. It varies widely, and the most effective versions set a clear bar.**
- *Eager:* Graphiti says "Capture requirements and preferences immediately… Be proactive: If you notice patterns in user behavior, consider storing them". The reference prompt captures identity, behaviours, preferences, goals and relationships in every conversation. Both are aimed at personalising chat, not at engineering knowledge.
- *Explicitly restrained:* Basic Memory says "Do not write unprompted… wait for agreement before writing". It frames this as "offer-not-act on purpose… so power-user / coding sessions stay unobtrusive", and adds that connections should be made "when they improve later retrieval, not to satisfy a quota".
- *Threshold-based:* Serena's shipped `memory_maintenance` says "Add or update memories only with stable, non-obvious project conventions that avoid complex rediscovery in the future. Do not add: quick-read facts; generic language/framework knowledge; one-off task notes; volatile line-level details; behavior likely to change soon." Its style rule is "Dense agent notes, not prose docs." ([memory_maintenance.md](https://github.com/oraios/serena/blob/abb0a0f01b94bc8050086f0fb860077d17730324/src/serena/resources/memory_maintenance.md)). Claude Code's auto memory "skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say. Claude doesn't save something every session. It decides what's worth remembering based on whether the information would be useful in a future conversation." ([memory docs](https://code.claude.com/docs/en/memory)).
- *Seeded conventions:* Before writing any project memory, Serena copies a `memory_maintenance` memory into the project and tells the Agent to read it first. The convention therefore lives in the store and can be edited ([docs](https://github.com/oraios/serena/blob/abb0a0f01b94bc8050086f0fb860077d17730324/docs/02-usage/045_memories.md)).
- *Nudges in tool results:* When Claude Code writes `MEMORY.md` near its limit, it "reminds Claude to shorten it: keep one line per entry, move detail into topic files, and merge or drop stale entries". Over the limit, it returns an error telling Claude to rewrite the index ([memory docs](https://code.claude.com/docs/en/memory)). The tool result is used to teach the Agent at the moment it acts.

**Lessons for us**
- SPEC §14 needs a **server instructions** text, under 4,096 characters with the critical rules first. It should cover: call `context` at the start of work in a Repository; `search` before investigating or deciding; what qualifies as a Recollection (the five Kinds); and, explicitly, what doesn't (anything derivable from code or git history, generic library knowledge, one-off task notes, line-level details likely to change). The last part is ADR-0002 restated as guidance for Agents. This belongs to #25.
- Put the trigger words in the first sentence of each tool description. With tool search, Claude matches queries against descriptions, and only the text within the shorter limit is searched.
- Consider `alwaysLoad` for `context` and `search` (and maybe `write`) so they don't have to be discovered through tool search. Only the server can set this, and each is a short definition.
- Use tool results to teach: `context` can end with a one-line reminder of pending obligations (Promotions, `unknown` Branches, files needing repair, stale counts), and a `write` rejection should tell the Agent exactly what to do next (see §3).
- Restraint and engineering knowledge go together. The systems aimed at coding (Claude Code, Serena, Basic Memory) all lean towards writing less, while the eager ones (reference server, Graphiti) are aimed at personalising chat. We should lean towards writing less.

## 3. Avoiding write spam and duplicates

**Exact-match deduplication only (reference server).** `create_entities` skips names that already exist. `add_observations` skips observation strings that are already present. `create_relations` skips identical triples ([index.ts L578](https://github.com/modelcontextprotocol/servers/blob/ef9808f71090d0db3eda99e2af2ba78f1086f4fb/src/memory/index.ts#L578), [L785](https://github.com/modelcontextprotocol/servers/blob/ef9808f71090d0db3eda99e2af2ba78f1086f4fb/src/memory/index.ts#L785)). A reworded observation is stored as a new one. Issue #3953 calls the result "Observation Bloat: No built-in mechanism exists to split, archive, or reorganize oversized observations".

**Similarity advisory after a create (Basic Memory), the closest analogue to SPEC §5.3.** After a new note is created, the server searches for its nearest neighbours ([similar_notes.py](https://github.com/basicmachines-co/basic-memory/blob/4bcfc0665744960f514a0ff61f4f432aa8cfe54f/src/basic_memory/mcp/similar_notes.py)):
- It returns at most **3** neighbours: "a longer list adds noise, not signal".
- The probe is the note's title plus the start of its body, up to 900 characters, "to land in the same neighborhood as the note itself".
- The threshold is **0.70** on bge-small-en-v1.5, which is stricter than search's 0.55 relevance threshold. It was measured: "rewrites of an existing note scored 0.77-0.93 against it…, while the nearest neighbor of a note on an unrelated topic topped out at 0.67". The code adds: "The number holds for that model only."
- Scores are **hidden**: "on the default model a near-duplicate and a merely related note score in the same band, so a number would imply a precision the signal does not have. Ranking is the useful part."
- Notes the new note already links to are **excluded**: an existing link is "the advisory's 'related but distinct' answer given in advance".
- The output is a decision table. "Did you mean to write to one of these?" is followed by: *same topic* → write to the closest note instead; *related but distinct* → add a `relates_to` link; *unrelated* → nothing to do.
- The advisory **doesn't block** the write ([write_note.py L91–95](https://github.com/basicmachines-co/basic-memory/blob/4bcfc0665744960f514a0ff61f4f432aa8cfe54f/src/basic_memory/mcp/tools/write_note.py#L91-L95)). The guide adds a behavioural rule: "Use `bm_search` before creating a note so related knowledge is reused instead of duplicated."

**Server-side LLM resolution (Graphiti, Mem0).** Graphiti runs entity and edge extraction, deduplication and summarisation through an LLM for each episode. Contradicting facts get `invalid_at` set rather than being deleted ([README](https://github.com/getzep/graphiti/blob/5c27edfa8d3e0f49b2571bcebb4261bcc89ee037/README.md)). The Mem0 plugin takes writing away from the Agent altogether. Hooks record the session, and "after every five completed exchanges, a detached background worker sends that batch to Mem0", where it is extracted and categorised. Its `remember` skill tells Claude to restate the fact clearly, because "your visible reply is what memory extraction reads" ([README](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/integrations/claude-code-plugin/README.md), [remember skill](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/integrations/claude-code-plugin/skills/remember/SKILL.md)). Both approaches need an LLM and background work. Graphiti's own docs warn about LLM-provider 429 errors during ingestion. ADR-0005 rules out the background part, and ADR-0002's goal of distilled, curated knowledge argues against capturing whole transcripts.

**Clutter control (Anthropic memory tool, Claude Code).** The API docs suggest reinforcing "Do not create new files unless necessary… You can rename or delete files that are no longer relevant", capping file sizes and `view` output, and expiring files that haven't been accessed for a long time ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Claude Code notes that "if two instructions contradict each other, Claude may pick one arbitrarily", and offers `/doctor prompt-audit` to find conflicts ([memory docs](https://code.claude.com/docs/en/memory)).

**Lessons for us**
- Keep the similarity check, and adopt Basic Memory's shape for its response. Return at most about 3 candidates, ranked, without raw scores. For each, give the next step in our own terms: *same knowledge* → `update` or `supersede` the existing Recollection; *related but distinct* → retry with a `relates-to` Link (and `distinct: true`); *unrelated* → retry with `distinct: true`.
- Leave out candidates the new Recollection already Links to with `relates-to`, and have that Link count as `distinct`. Then Agents can follow the "related" path without a second flag.
- **Calibrate the threshold on our own model using `brain eval`** (SPEC §13). Add pairs of rewrites and near neighbours to the fixture brain. Basic Memory's numbers (rewrites 0.77–0.93, unrelated at most 0.67, cutoff 0.70) are a starting point for bge-small only. The threshold must be stored with the embedding model ID, like the dimensions in SPEC §6.1.
- Our design **rejects** the batch where Basic Memory only advises. That is stricter. The risk is that Agents learn to always send `distinct: true`. Ways to reduce it: write the rejection message as the decision table above, and consider requiring a short `distinct_reason` that goes into the commit trailer so it can be audited later. *(Open question, below.)*
- Basic Memory keeps a separate, explicit overwrite rule, and so do we: `create` never overwrites, and `update` requires an existing ID. Keep that.
- Our `supersede` covers what Graphiti's fact invalidation does, and git history keeps the old version. No further mechanism is needed.

## 4. Reported failure modes

| Failure | Where reported | Our status |
|---|---|---|
| A whole-store read consumes 50–80k tokens; there's no metadata-only or paged read | servers [#3953](https://github.com/modelcontextprotocol/servers/issues/3953) | Avoided by `search`/`get`; add budgets to `get` and `context` |
| Observations pile up with no way to split, archive or reorganise them | #3953 | `supersede`, `delete` and git history cover it; the guidance should encourage folding into existing Recollections |
| Default storage inside the package directory, lost on reinstall | servers [#4117](https://github.com/modelcontextprotocol/servers/issues/4117) | Avoided: `$XDG_DATA_HOME`, git remote (ADR-0004) |
| Whole-file writes, no lock, concurrent hosts corrupt state | #4117 (the reference server has since added a lock file and atomic save, per its README) | Avoided: one file per Recollection, lock, WAL (SPEC §11) |
| Destructive tools with no audit trail or undo | #4117 | Avoided: every batch is a commit; `history` (SPEC §5, §14) |
| Secrets kept in memory | #4117 | Covered: secret check on `write` (SPEC §5) |
| **Memory becomes a "persistent prompt-injection" surface** when fetched content or logs are stored | #4117 | **Not covered**: nothing tells Agents to treat Recollection text as data rather than instructions |
| Memory from unrelated contexts mixed in one global store | #4117 | Avoided: scoping by Repository and Branch (SPEC §6.4) |
| Agent doesn't actually write memories at the end of a long task | Serena docs: "If an LLM fails to complete the onboarding and does not actually write the respective memories to disk, you may need to ask it to do so explicitly" | Open: we have no hooks; this depends on #25 |
| Contradictory memories, model picks one arbitrarily | Claude Code memory docs | Partly covered: `supersede` and duplicate candidates; there's no contradiction check |
| Ingestion cost and 429 errors from server-side LLM extraction | Graphiti README | Not applicable: no LLM in the write path |

## Newly surfaced questions

1. **Server instructions text and channels.** We need the actual instructions text, at most 4,096 characters with the most important rules first, and a decision on whether to set `anthropic/alwaysLoad` on `context`, `search` and `write`. *(Feeds #25 and #24.)*
2. **Session-end capture without background processes.** Serena and Mem0 both show that Agents often don't write at the end of a task. Mem0 solves this with hooks plus a background worker. Should v1 ship an optional Claude Code plugin or skill whose `Stop`/`PreCompact` hook prompts the Agent to consider a `write`? That runs in the client, not in `brain`, so it doesn't conflict with ADR-0005. *(Feeds #25.)*
3. **Duplicate check: reject or advise, and how to stop `distinct: true` becoming a reflex.** Options: keep rejection but return a decision table; let a `relates-to` Link count as `distinct`; require a `distinct_reason` recorded in the commit trailer. *(Feeds #10 and #24.)*
4. **Duplicate threshold per model.** `brain eval` should measure the duplicate threshold as well as recall, using pairs of rewrites and near neighbours. *(Feeds #5 and #10.)*
5. **Prompt injection from stored Recollections.** Should the instructions and `get` output frame Recollection bodies as untrusted data? Should `write` refuse content that looks like instructions to an Agent?
6. **Optimistic concurrency on `update`/`supersede`.** Should these operations carry the `updated` timestamp or hash the Agent read, and be rejected if the file has changed since? *(Feeds #24.)*

## Implied SPEC changes

- **§14:** add a "Server instructions" subsection with the text, or a pointer to where it lives, a 4,096-character limit, and the rule to put the important parts first. Add MCP tool annotations (`readOnlyHint` on read tools; `destructiveHint` on `write`). Add output budgets to `get` and `context`.
- **§5, check 3:** say what the rejection response contains: at most about 3 ranked candidates, no scores, and a decision table naming `update`/`supersede`, `relates-to` plus `distinct`, or `distinct`. Leave out candidates already Linked by `relates-to`. Store the threshold for each embedding model, calibrated with `brain eval`.
- **§13:** extend `brain eval` to report how well duplicate detection separates rewrites from neighbours.
- **§5 (possibly):** an optional precondition on `update`/`supersede`.
